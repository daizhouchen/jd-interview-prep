# AI PM 经典考题域：思想地图 + 三档对比

这份 reference 是 AI PM 面试的"思想军火库"。AI PM 这个职业**和传统 PM 的核心差异**在于：你要在不可控的概率系统上做产品决策。这份 reference 教 skill 怎么把 AI PM 面试的高频考点变成"认知地图"——不是给标准答案，是把每个考点的思维结构展开。

---

## 开篇：AI PM 这个职业的本质

### 三个本质判断

**判断 1：AI PM 不是"用 AI 做 PM"，是"做 AI 这种东西的 PM"**

普通 PM：定义"做什么 / 给谁 / 长什么样"。
AI PM：还要定义"用多确定的能力做 / 容忍多大错误 / 错了怎么兜底"。

这意味着 AI PM 必须懂三件传统 PM 不需要懂的事：
- **概率系统的产品语言**（不是 0/1 而是 0.0-1.0 的产品体验设计）
- **eval 即产品**（你 eval 什么，决定产品成什么样）
- **数据飞轮**（不是"上线就完了"，是"上线开始才是收集数据的开始"）

**判断 2：AI PM 的稀缺能力是"翻译"**

AI 圈和应用圈用两种完全不同的语言。AI PM 是夹在中间的翻译器：
- 把"模型有 hallucination 但 retrieval 增强后召回率从 60% 提升到 85%"翻译给业务方："我们能把答错率压到 15% 以内，但还需要做一个用户校验环节兜底"。
- 把"客户需要一个能自动审单的系统"翻译给算法："这是一个二分类 + 解释 + 审计追踪的复合任务，不是一个端到端 LLM 直出方案"。

**翻译能力 = AI PM 的护城河**——这一点应该在面试任何一个具体技术问题时都能体现。

**判断 3：AI PM 的最大失败模式是"被技术 narrative 牵着走"**

很多 AI PM 失败在：模型出新功能，PM 跟着加；论文出新方法，PM 跟着试；竞品出新形态，PM 跟着抄。

成熟的 AI PM 会问：**"这个新能力解决了哪个用户的哪个具体痛点？我有没有用代理指标骗自己？"**

这套**反 narrative 的提问能力**是面试中最容易体现"你和别人不一样"的点——很多面试官会有意问"你怎么看 [最新热门概念]"，这是 framing 题，不是知识题。

## 考题 1 · eval 设计（最高频，必考）

### 认知地图

```
                     eval 这件事的全图
                            │
            ┌───────────────┼───────────────┐
        离线 eval        在线 eval         人评 eval
        （回归集）       （A/B + 遥测）     （专家+众包）
            │               │               │
        什么时候用？    什么时候用？     什么时候用？
        - 模型迭代前   - 上线后持续   - 主观/复杂任务
        - 快速判断     - 真实分布反馈 - 要 ground truth
        - 大批量测试   - 因果归因      - 训 judge model
            │               │               │
        指标常见：      指标常见：      指标常见：
        - 准确率/F1     - 任务成功率   - 5 档 likert
        - hit@k         - 用户保留     - 维度细分
        - LLM-as-judge  - 反馈率        - 共识度
            │               │               │
            ↓               ↓               ↓
       ── LLM-as-judge 是当代 AI PM 的核心武器 ──
       ── eval 设计本身就是产品决策 ──
       ── 没有 eval 的 AI 产品，等于在闭眼开车 ──
```

### 关键判断（面试必备）

1. **离线 eval 必须 + 在线 eval 必须 + 人评 eval 关键场景必须**——三件套，缺一不可。
2. **LLM-as-judge 是杠杆但有 bias**——judge 模型对长答案打高分、对自家模型友好。**对策**：人工抽样标 5-10% 校准 judge。
3. **eval 集要刻意管理**——不只是"放几个测试样例"，要按用户分布抽样、要保证有 edge cases、要定期更新（不然 eval 集和真实分布脱节）。
4. **eval 设计本身就是产品决策**——你 eval 什么，团队优化什么，产品最后就是什么样。所以 eval 框架要在产品定义阶段就确定，不是上线前临时拼。

### 三档对比："你怎么做 eval"

**弱**：
> "我们用了准确率作为指标，跑了一些测试集。"

**合格**：
> "分了离线和在线两套：离线用一个 200 条的标注集跑 hit@5；在线看用户反馈率。"

**惊艳**：
> "eval 在我做的 RAG 项目里经历过三次迭代，这是我对 AI eval 形成的判断：
>
> **第一次**：用 hit@5。分数好但用户反馈差。原因——hit@5 衡量的是召回，但用户在乎的是'前 3 个里有没有真正解答我的问题'，这是 helpfulness 不是 retrieval。
>
> **第二次**：换 LLM-as-judge，让 GPT-4 评估 'answer helpfulness 1-5 档'。分数和用户反馈对齐多了，但发现 judge 偏长答案——同样质量的回答，长的就被判 4 分、短的判 3 分。
>
> **第三次**：混合 eval——60% LLM-judge（用 GPT-4 + 严格的 rubric prompt 来减 bias）+ 30% 人工抽样（200 条/月）+ 10% 真实用户反馈（直接采集 thumbs up/down）。三层互相校准。
>
> 这个项目让我形成的核心判断是：**eval 不是工程问题，是产品决策**——你 eval 什么，团队就优化什么，产品最后就长什么样。所以我现在做任何 AI 应用，第一周做的事就是先和 PM 团队对齐 'eval 优先级'——这一步比写 PRD 还前置。"

注意"惊艳"档做对了什么：
- 不是"我知道几个 eval 方法"，是"我经历过迭代"
- 每次迭代的**原因**讲清楚（不是"试了下"）
- 提取出可迁移的**判断**（"eval 不是工程问题，是产品决策"）
- 把这个判断**应用到现在的工作方式**（"第一周做 eval 优先级对齐"）

## 考题 2 · Hallucination（幻觉）治理

### 认知地图

```
        Hallucination（模型幻觉）治理的产品视角
                          │
        ┌─────────────────┼─────────────────┐
   减少发生              控制影响          检测+恢复
   （Prevention）        （Mitigation）    （Detection）
        │                   │                  │
   - RAG 接地实
   - 工具调用约束
   - 提示工程               - UI 警示提醒    - 一致性检测
   - 模型选型               - 置信度展示    - 用户反馈通道
   - SFT 数据清洗           - 关键操作二次确认 - 自动 LLM-as-judge
   - 输出格式约束           - 兜底人工流程    - 异常 pattern 监控
        │                   │                  │
        ↓                   ↓                  ↓
   ── 单点防御都不够，必须三层叠加 ──
   ── Hallucination 不能"消除"只能"管理" ──
   ── 用户对幻觉的容忍度 = 任务的可逆性 ──
```

### 关键判断

1. **Hallucination 不是 bug，是 LLM 的固有属性**。承认这一点，从"消灭它"转向"管理它"。
2. **任务可逆性决定容忍度**——写营销文案出错可改；下单/转账/医疗建议出错不可改。前者可以放手让模型干，后者必须人工兜底。
3. **置信度展示是产品义务**——AI 产品不展示置信度 ≈ 让用户在不知情状态下相信概率系统，是产品伦理问题。
4. **降低用户期望也是治理手段**——产品文案上写"AI 助手，仅供参考"vs 不写——用户的容忍度差很多。

### 三档对比："你怎么处理 hallucination"

**弱**：
> "我们用了 RAG 来减少幻觉。"

**合格**：
> "三个层面：(1) RAG 增强引用真实文档；(2) 输出加引用源给用户校验；(3) 用户能反馈，反馈进 eval 集。"

**惊艳**：
> "我对 hallucination 治理的判断是 **'不能消除只能管理'**——所以我做产品时分三层考虑：
>
> **预防层**：选模型的时候不只看 benchmark，看的是'在我目标领域'的 hallucination rate；做 RAG 时把 retrieval recall 推到 90%+ 比把生成精度推到 95% 更值得；prompt 里加约束（'仅基于以下文档回答'）能降 30%-40% 出错率。
>
> **缓解层**：UI 上必须展示来源（可点开看原始文档）；高风险操作（涉及金额/医疗/合规）强制人工二次确认；输出长度有约束（越长越容易飘）。
>
> **检测层**：上线后用 LLM-as-judge 对 5% 流量做一致性检测；用户反馈直接进 eval pipeline；建立'异常 pattern 检测'——如果某类 query 出错率突涨，自动告警。
>
> 这套思路下，**最关键的判断是任务的可逆性**——写营销文案出错可以改，所以我们容忍 5%-10% 错误率换效率；金融建议出错不可逆，必须接近 0% 错误率，宁愿牺牲覆盖率。**容忍度的产品决策必须在最早期就明确**，决定后续所有架构。"

## 考题 3 · RAG vs Fine-tune vs Agent 决策框架

### 认知地图（决策树）

```
                    "我应该用什么 AI 方案"
                            │
                            ↓
                  问题是什么类型？
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
        信息检索/QA    任务执行/工作流  风格/口吻定制
              │             │             │
              ↓             ↓             ↓
            首选 RAG       首选 Agent    首选 Fine-tune
              │             │             │
        什么时候补 FT？   什么时候补 RAG？  什么时候补 RAG？
        - 领域术语        - 需要外部知识  - 需要事实准确
        - 输出格式严格    - 需要上下文记忆 - 需要可追溯
              │             │             │
        什么时候补 Agent？什么时候补 FT？  什么时候补 Agent？
        - 多步推理        - 工具调用稳定性差 - 需要主动调工具
        - 需要工具调用    - 特殊领域语法
```

### 关键判断（面试必备）

1. **第一性问题永远是"问题类型"**——别人推什么不重要，看你的具体场景：是查信息、是干活、还是模仿风格。
2. **RAG 是默认起点**——便宜、可控、可追溯。除非有强理由别先上 FT 或 Agent。
3. **FT 的代价高于看上去**——不只是训练成本，是**模型版本管理 + eval 重做 + 数据清洗 pipeline 维护**——你买了一头牛，每个月要喂草。
4. **Agent 的瓶颈不在框架，在工作流定义**——99% 的"做不出 Agent"案例不是技术问题，是 PM 没把工作流抽象清楚。

### 三档对比："你怎么决定用 RAG 还是 Fine-tune"

**弱**：
> "看具体情况。RAG 适合查询，FT 适合定制。"

**合格**：
> "三个维度判断：(1) 知识时效——动态选 RAG，静态可 FT；(2) 数据量——少 RAG 多可 FT；(3) 输出可控性——FT 更可控但维护贵。"

**惊艳**：
> "我的判断框架有 3 个层次：
>
> **第一层 · 问题类型**：信息检索 → RAG，任务执行 → Agent，风格定制 → FT。这是默认起点。
>
> **第二层 · 现实约束**：
> - 数据条数 < 1000 → 不要 FT（不稳定）
> - 知识更新快（< 1 月一次）→ 强烈倾向 RAG
> - 团队没有训练经验 → 不要碰 FT（学习曲线和踩坑成本高于收益）
> - eval 还没建好 → 任何方案都先暂停
>
> **第三层 · 隐性成本**：FT 的真实成本不是训练，是后续——模型每次升级要重训、eval 要重做、数据清洗 pipeline 要维护、A/B 实验复杂度倍增。我做过的项目里，FT 真正 ROI 正的不到 30%。
>
> 所以我现在的默认推荐是：**先 RAG，eval 跑通；不够好再考虑 SFT 个小模型；除非确认必要，避免 FT 大模型**。Agent 只在多步任务且工作流能被清晰抽象时才上。
>
> 这个框架在火山方舟做企业落地时尤其适用——B 端客户预算有限、知识更新频繁、人才稀缺，'先 RAG 后再说'是最务实的起点。"

## 考题 4 · Cost-Quality-Latency 三角

### 认知地图

```
                    Cost ──────────── Quality
                       \              /
                        \            /
                         \          /
                          Latency
                  (任何两个变好，第三个一定退)
```

三角约束。**面试官常用问题**："如果让你做一个 [某场景] 的产品，你怎么权衡这三者？"

### 关键判断

1. **没有"三全其美"——任何架构选择都在做这三个的取舍**。
2. **场景决定优先级**：
   - C 端实时聊天：latency 优先 > quality > cost
   - B 端审单：quality 优先 >> cost > latency
   - 内部内容生成：cost 优先 > quality > latency
3. **Cache 是隐藏的解药**——很多场景靠 prompt cache + result cache 能把三个一起优化。
4. **不要用大模型做小事**：路由（router）模式——简单 query 用小模型，复杂 query 用大模型。是最 underrated 的优化。

### 三档对比："你怎么做成本控制"

**弱**：
> "选便宜的模型。"

**合格**：
> "用更小的模型 + cache + batch + 短 prompt。"

**惊艳**：
> "成本控制的核心不是'省'，是'匹配'——把对的能力用在对的地方。
>
> **架构层**：用 router——一个轻量分类器（甚至是规则）先判断 query 类型，简单的走 GPT-3.5/Doubao-Lite，复杂的走 GPT-4/Doubao-Pro。这一步通常能砍 60-80% 成本。
>
> **缓存层**：prompt cache（OpenAI / Anthropic 都支持）能砍重复 prompt 的成本；语义 cache 能识别'用户问了类似的问题'直接返回历史答案。
>
> **优化层**：prompt 长度（input token 是隐藏成本巨头，stuff 不必要的 context 是常见错误）；输出长度约束（max_tokens 该卡就卡）；batch（非实时场景必用）。
>
> **业务层（最重要）**：和业务方对齐'你愿意为多少质量付多少钱'。很多时候业务想要 95% 准确率但 80% 已经够用，5% 额外准确率的成本可能是 5x。这种对齐是 AI PM 的核心价值。
>
> 火山方舟做企业落地，我猜成本是 B 端客户最敏感的话题——一个能讲清楚成本结构 + 提供 router 化方案的 PM，比'用 GPT-4 做一切'的 PM 价值高 10 倍。"

## 考题 5 · 数据飞轮（Data Flywheel）

### 概念

数据飞轮 = 用户使用产生数据 → 数据改进模型 → 模型变好吸引更多用户 → 更多数据。

**AI 产品的护城河 = 数据飞轮的转速**。

### 设计要点

1. **反馈通道是产品义务**——thumbs up/down、隐式反馈（停留时长、是否复制）、bug report
2. **反馈数据要进 eval/training pipeline**——如果反馈进了死湖，飞轮不转
3. **冷启动方案**——飞轮没启动前怎么办？合成数据 / 公开数据集 / 行业 partnership / 人工标注
4. **数据闭环 ≠ 数据采集**——采集了不分析、分析了不入产品改进，等于没飞轮

### 三档对比："你的产品怎么形成数据飞轮"

**弱**："让用户多用，数据自然就多了。"

**合格**："产品里加 thumbs up/down 收集反馈，数据每月 review 一次，反馈进 eval 集。"

**惊艳**：
> "数据飞轮的设计有三个核心要点：
>
> **(1) 反馈密度**——光给 thumbs up/down 是低密度反馈。我会设计'分维度反馈'：'回答准确性' / '相关性' / '清晰度' 三档，每个 1-5。低密度反馈给的信号弱到无法直接用，分维度的能直接进 eval rubric。
>
> **(2) 反馈→产品的闭环时长**——用户给的反馈，多久能影响产品？这是飞轮的转速。我做过的项目里，最快的能做到 'T+1 天反馈进 eval 集 + T+7 天进 prompt/model 优化 + T+14 天 A/B 验证'。这个节奏决定护城河厚度。
>
> **(3) 冷启动 + 长尾**——飞轮没启动前的合成数据生成路径要早设计；飞轮转起来后要警惕'高频用户偏好覆盖低频用户'——常见的反例是模型越优化越擅长服务老用户，新用户体验越差。要专门切'新用户首周'切片做 eval。
>
> 这个框架对 B 端 AI 解决方案特别重要——B 端用户少、反馈少，飞轮天然弱。所以做行业方案时要主动构造'拟反馈'——让客户的领域专家参与定期 review，把他们的判断当高质量人评数据进 pipeline。"

## 考题 6 · AI 安全的产品视角

### 关键判断

AI 安全在产品层面分 4 类：
1. **内容安全**——不出违法内容、不出歧视言论、不泄露 PII
2. **行为安全**——Agent 不做不该做的事（特别是工具调用类）
3. **数据安全**——客户数据不被训练污染、不跨租户、不被反向工程
4. **越权安全**——用户不能通过 prompt injection 让模型超出权限

面试时**不要把 AI 安全讲成"加个过滤器"**——这是行业常见的肤浅理解。

### 三档对比："AI 安全你怎么考虑"

**弱**："我们加了内容审核。"

**合格**："分输入审核、输出审核、操作审核三层。"

**惊艳**：
> "AI 安全在产品层面我会分 4 个维度看：
>
> **内容安全**——多模态 + 多语言双重难点。仅靠规则审核会假阳性高、假阴性也高，最佳实践是'分层审核'：硬规则过滤（明确违法）+ 模型审核（边界模糊）+ 人工兜底（高敏感）。
>
> **行为安全**——Agent 时代特别重要。Agent 工具调用要做'权限白名单 + 操作幂等性 + 关键操作二次确认 + 完整审计日志'。我对 Agent 安全的判断是：**不要把'权限'外包给 LLM 决策**，权限永远应该由确定性代码兜底。
>
> **数据安全**——B 端 AI 平台的核心命题。火山方舟做了 ISO 42001 + 等保三级，这是 B 端 AI 服务的入场券。除了认证，更难的是**架构层面的数据隔离**——多租户怎么保证客户 A 的数据不会通过模型 prompt cache 泄露到客户 B、私有化部署的更新策略怎么不污染客户的微调数据。
>
> **越权安全**——prompt injection 是当代 AI 应用的'SQL injection'。每个接受用户输入并调用模型的产品都要测：用户能不能通过特殊 prompt 让模型违反系统指令。我做产品时会专门有一个 red-teaming pipeline，定期跑公开 jailbreak 数据集 + 自己构造的 case。
>
> 在 AI Application 解决方案场景下，这 4 个维度直接决定一个客户敢不敢上线——所以一个能从 4 维讲清楚安全的 PM，对客户的说服力远高于只会说'我们有内容审核'的 PM。"

## 考题 7 · "你怎么看 [当前热门话题]" （Framing 题）

### 这类题的本质

这不是知识题，是**framing 题**——评估你能不能在不熟悉的话题上**给出非显然判断**。

常见话题（2026 视角）：
- "你怎么看 Long-horizon agent"
- "你怎么看 GPT-5/Claude/Doubao 这一代模型"
- "你怎么看 AI Coding"
- "你怎么看 AI 视频生成"
- "你怎么看开源 vs 闭源"
- "你怎么看中美 AI 差距"

### 应对框架（3 步）

```
1. 给一个具体框架/分类（让对方知道你不是凭感觉）
2. 给一个非显然的判断（避免共识，要有立场）
3. 用一个具体例子收尾（让判断落地）
```

### 三档对比："你怎么看 AI Agent 这条赛道"

**弱**："Agent 是未来趋势，长期看好。"

**合格**："Agent 还在早期，瓶颈在 reasoning 和 tool use 鲁棒性，看好 long-horizon agent 在客户成功场景的落地。"

**惊艳**：
> "我对 Agent 的判断有两层：
>
> **第一层 · 短期（6-12 个月）**：Agent 商业落地的瓶颈不是模型能力，是**工作流定义**。我接触过几个 B 端客户，他们想'用 AI 自动化客户答疑'——但当我问'你现在的客户答疑工作流是什么'时，他们自己都讲不清楚。**Agent 不能自动化你定义不清楚的东西**。所以这 6-12 个月，Agent 落地真正稀缺的是'懂工作流抽象'的 PM 而不是更强的模型。
>
> **第二层 · 中期（2-3 年）**：随着 reasoning 深化（o1 / Claude with thinking 这类），Agent 会从'替代任务'走向'替代角色'——比如不是替代'查询订单'这一步，是替代'客户经理'这个角色。这时候真正的护城河是**和角色相关的私域数据 + 反馈闭环**——谁能让 Agent 在'客户经理'这个角色上越用越懂客户、越懂业务、越懂行业，谁赢。
>
> **具体例子**：火山方舟现在的 Agentic RAG——我理解就是把'工作流定义'层的能力下沉给客户。这个切入点比纯做 Agent 框架更稳，因为它和客户现有 SOP 直接对接，迁移成本最低。"

## 考题 8 · 简历项目深挖

参见 narrative-architecture.md 的"项目深挖（3 层讲法）"。AI PM 简历项目深挖的特殊点：

1. **必问"你怎么做 eval"**——简历上的 AI 项目没说 eval = 大概率被深问
2. **必问"模型选型理由"**——为什么不用 GPT-4 / 为什么用 Doubao / 为什么自训
3. **必问"成本和延迟"**——上线规模 + 单次调用成本 + p95 latency
4. **必问"和谁协作 / 你的 ownership"**——是你定的还是跟着做

简历项目最常见**致命弱点**：**没数据、没规模、没 eval**——这三个缺一个都会被怀疑"是不是真做过"。

### 反例

❌ 简历："基于 LangChain 搭建 RAG 系统，效果良好。" → 任何面试官追问 5 个问题就破防。
✅ 应该："基于 LangChain 搭建医疗 RAG，对接 200+ 临床指南文档，服务 500 名医生用户日均 2k query，hit@5 88%、helpfulness 4.1/5（基于人评 200 条/月），p95 latency 2.3s，月成本约 $400。"
